# v0.7.101 — RPC priority recovery

PAPER, порт 8188. Торговые пороги, лимит RPC 6/с и 4 in-flight, 0,75 с на допуск, свежесть банка и условия продажи сохранены.

P0-1. Чтение exit_priority_v94
- PermissionError и Windows 5/32/33 при чтении/перечислении файлов приоритета дают PRIORITY_READ_BUSY: локальный повтор внутри прежнего дедлайна, затем Deferred. HTTP до успешного чтения не выполняется. Слоты и metadata.lock отпускаются; ожидание не удерживает metadata.lock.
- Новый отказ чтения не создаёт постоянный control_failed.json. В priority_read_v101.json сохраняются этап, тип, errno/winerror и безопасные frames/chain без URL, ключей и произвольного текста исключения. Маркер контролируемой инъекции размечается отдельно.
- Неизвестные/повреждённые JSON, backlog, неизвестные I/O и неподтверждённые исходы остаются fail-closed. Нечитаемый маркер ошибки не считается отсутствующим. Общая atomic_json и команды STOP не ослаблены.

P0-2. Уже сохранённая защёлка
- Существующий запуск сам её не снимал: прежний recovery допускал только подтверждённые ошибки записи HTTP-результата.
- Для ТОЧНОГО инцидента из preservation_20261031_202416_769378 добавлено аудированное восстановление. Проверяются SHA256 исходного маркера, полный логический снимок settings/endpoints/receipts, файлы rate, отсутствие ожидающих исходов, целостность БД и доступность всех четырёх слотов под metadata.lock; текущие priority leases должны читаться и проходить проверку.
- Исходный control_failed.json сохраняется побайтно. Создаётся привязанная к его хешу и текущей БД квитанция восстановления. Счётчики, rate/cooldown, исходы и торговые БД не сбрасываются.
- Отличающийся маркер, другой снимок БД/лимитов, повреждённый rate-файл, ожидающий outcome, занятый слот или недоступный приоритет запрещают восстановление. Это не универсальный автоматический сброс любых ошибок. Не удалять control_failed.json вручную.
- 14_RPC_STATUS.bat выполняет этот ограниченный recovery и ОДИН read-only getGenesisHash через настоящий общий регулятор. Проверяется mainnet identity. Отчёт: app/data/rpc_resume_status_v101.json. Для восстановленного старого контроля started_total должен вырасти с 734 минимум до 735. У новой чистой папки свой счётчик: проверяется рост относительно её собственного before, а не число 734.

P0-3. Подтверждение остановки
- До запуска веток сохраняется план текущего PRIMARY run, затем привязываются фактически запущенные session IDs.
- При AMM_BRANCH_ENABLED=0 ожидается только ROUTE. Для включённых веток отсутствие ACK, чужая session, forced/monitor_forced или неполный/повреждённый план остаются ошибкой.
- Смена настройки после старта не меняет ожидаемый состав. Для данных без нового плана действует прежняя консервативная проверка обеих веток; неизвестный план не считается успешной остановкой.

Продолжение кампании с открытой позицией
1. Старый бот должен быть остановлен, процессы завершены. Сохранить старую папку и исходный preservation без изменений. Старые 3 PAPER не считать закрытыми.
2. Распаковать ZIP в НОВУЮ папку pumpfun_bot_v0.7.101_rpc_priority. 01_INSTALL → 02_SETTINGS. Импортировать через настройки прежние разрешённые API/параметры; не менять торговые пороги. Private key не вводить.
3. Для ПРОДОЛЖЕНИЯ той же кампании перенести целиком app/data остановленной v0.7.100.1 в ещё пустую app/data новой папки. Сохранить все PRIMARY/ROUTE/monitor/control DB и их сопутствующие файлы. Не смешивать БД разных кампаний и не переносить только primary.db. Если в новой app/data уже есть тестовые данные, сначала сохранить эту папку отдельно, затем заменить её целиком. Старую исходную папку не удалять. .env переносится через 02_SETTINGS, путь DATABASE_PATH остаётся data/clean_0762.db; RPC_CONTROL_DIR должен указывать на выбранную копию, а не случайно на другую работающую установку.
4. Выполнить 04_CHECK до конца. Его отчёт recovery не заменяет техническую часть. Старые results/recovery/acceptance из другой версии не копировать.
5. Запустить 14_RPC_STATUS. Требуются recovery_applied=true для старой защёлки, after.status=READY, probe.status=PASS, started_after>started_before. При отказе сохранить отчёт; сбрасывать маркер/БД вручную не нужно.
6. Для обычного PAPER — 03_START. Для нового чистого теста можно оставить новую пустую app/data, сохранив старую кампанию отдельно как незавершённую; считать старый остаток реализованным нельзя.

Двухчасовой контролируемый PAPER-прогон
- 15_PAPER_FAULT_TEST.bat запускает обычный launcher с тем же источником и единственным рыночным сокетом. Дополнительный WebSocket не открывается.
- Через 3600 с от нажатия кнопки все PAPER RPC-читатели получают синтетический PermissionError при проверке приоритета в течение 10 с. Часы Windows не меняются, файлы прав доступа не меняются. Это моделирует отказ, а не доказывает его внешнюю причину.
- В 7200 с launcher идёт по своему штатному пути остановки, как при Ctrl+C. Позиции не закрываются искусственно. Ручной Ctrl+C доступен раньше.
- Отчёт app/data/rpc_fault_paper_v101.json: наблюдалась ли именно эта инъекция, увеличились ли started после окончания окна, осталась ли защёлка, завершён ли весь интервал. Ранняя остановка или blocked startup заменяют старый PASS новым незавершённым/ошибочным результатом. Если после окна не было новых запросов, восстановление этим прогоном не считается доказанным.
- Рост started доказывает новые допуски; успешность ответов и свежесть банков дополнительно проверяются в обычных отчётах RPC/монитора. PASS этого отчёта относится ТОЛЬКО к инъекции и возобновлению допусков RPC; закрытие всех ROUTE-позиций, AMM и стратегия проверяются отдельно. Никакого разрешения live он не даёт.
- Для трёх часов из локальной .venv можно вызвать bootstrap.py paper-fault-test --duration 10800 --fault-at 5400 --fault-for 10. Кнопка по умолчанию задаёт два часа.

После штатной остановки: 05_RESULTS. В review_bundle попадут отчёты проверки допуска и инъекции; RPC-контроль сохраняется отдельным вложенным evidence. Сначала присылать review_bundle, при необходимости preservation/тома БД. Генерация отчётов не исправляет и не обнуляет исходные БД.

Проверки в этой сборке: новые сценарии отказа/восстановления/плана веток/таймера включены в обязательный recovery. Контрольная модель воспроизводит старый снимок с started=734 и проверяет рост до 735 без удаления маркера. Проверяется также реальный локальный HTTP до/во время/после инъекции. Офлайн-тест таймера ускорен; физический 2–3-часовой PAPER-прогон на вашем Windows/провайдере здесь ещё не проведён. Нативная Windows-проверка новой версии требует вашего 04_CHECK.
