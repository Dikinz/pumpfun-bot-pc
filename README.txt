PUMPFUN BOT v0.7.76 — RECOVERY ADMISSION GATE

ИЗМЕНЕНИЕ v0.7.76
Причина завершения проверки и допуск исполнения учитываются отдельно.
SUPERSEDED_BY_EXIT_SIGNAL, INTERRUPTED_STOP, ошибки RPC/worker/cleanup
сохраняют исходный статус даже при закрытом допуске. result_json содержит
recovery_admission_v76: allowed, reason, state, session, epoch, job_epoch,
generation, classified_status. Исторические записи не переписываются.
Свежесть и epoch по-прежнему проверяются перед использованием симуляции;
старый пригодный результат получает RECOVERY_INVALIDATED и не закрывает слот.
Причина запрета теперь различает EPOCH_MISMATCH, JOB_NOT_AUTHORIZED,
состояние восстановления, устаревший pulse и ошибку записи состояния.
Закрытый допуск сам по себе не означает обнаруженную общую паузу.

УПРАВЛЯЕМАЯ PAPER-ПРОВЕРКА
04_CHECK автоматически запускает 41 отдельный тест восстановления/классификации
в дочернем процессе с временными базами. Для отдельного повтора после
01_INSTALL есть 09_RECOVERY_CHECK; ключи/RPC ему не нужны.
Отчёт: results/recovery_check_v76.json; включается в следующий 05_RESULTS.
Проверяется немедленный BUY после паузы 230 с, отсутствие изменения cash
и резерва от отклонённого входа, отказ старому PASS и заявке, отказ без нового
PASS, свежего соединения/тика, затем новый BUY с одним исполнением.
Отдельный сценарий сохраняет открытую позицию и SELL во время RECOVERING,
затем исполняет SELL по свежему тику после READY. Штатная отмена проверки
также проверена через asyncio cancellation, а не только прямой записью статуса.
Это контролируемая инъекция часов/рынка/отчёта PASS, не реальное усыпление
Windows. Временные базы удаляются; существующие торговые базы не открываются.
Сама 09-проверка не останавливает работающий бот и не доказывает live RPC.
RECOVERY_CHECK_v76.json в корне сборки — результат проверки при сборке Linux;
results/recovery_check_v76.json — локальный результат на вашем компьютере.

Полная чистая PAPER-сборка. Одна цель: проверяемый допуск после паузы.

СОСТОЯНИЯ
READY — штатный допуск (остальные проверки стратегии/свежести действуют).
RECOVERING — новые входы и исполнения PAPER заблокированы; мониторы
продолжают собирать данные. Позиции, деньги и исходные SELL-сигналы сохраняются.
STOPPED — primary завершён. Это не подтверждение восстановления после паузы.

ТРИГГЕРЫ И ПОКОЛЕНИЯ
Guard использует существующие диагностические границы: разрыв цикла >3 с
и wall-vs-monotonic jump >clock_lab.JUMP_MS (20 мс) с учётом погрешности
парного измерения. Пороги watchdog/стратегии/свежести не изменены.
Проверка выполняется также перед входом и на границах приёма сокета, чтобы
возобновившаяся рыночная задача не обошла ещё не запущенный heartbeat.
Каждая пауза/скачок создаёт новое случайное поколение epoch. Предварительные
проверки, BUY-заявки, тики и monitor jobs получают метку поколения.
Допаузные разрешения/результаты после восстановления не становятся пригодными.
Незавершённые BUY истекают по прежнему монотонному таймауту, сохраняются в БД.
Исторические факты исполненных сделок и зеркалирование общего лота не стираются.

ВОССТАНОВЛЕНИЕ
Для нового READY требуются одновременно:
1. Новое соединение PumpApi после барьера (старый сокет пересоздаётся).
2. Свежий проверенный тик: прежние 1 с, provider timestamp без будущего допуска,
   канонические source/pool/quote, signature и provider_price.
3. Новый PASS time_check.collect в текущем поколении после барьера.
Используется прежняя диагностика ±50 мс с прежними параметрами измерений;
это диагностическая оценка, не изменение торгового допуска 0 мс и не гарантия
достоверности timestamps провайдера. Часы не переводятся, w32tm resync не вызывается.
Старый PASS или ответ проверки из предыдущего поколения не разблокирует входы.
При не-PASS/ошибке состояние остаётся RECOVERING; повтор не чаще прежнего
интервала clock_lab.INTERVAL=120 с. Новый скачок снова меняет поколение.
Реальный допуск BUY по-прежнему требует нового пригодного preflight.

МЕЖДУ ПРОЦЕССАМИ
Primary публикует сессионное состояние и pulse раз в секунду; пульс старше
той же границы 3 с, недоступный/нечитаемый файл закрывают допуск клиентов.
Ветки/мониторы сами наблюдают разрыв времени; при своей паузе запрашивают
новое поколение primary. Запрос привязан к epoch, старый файл не действует
на следующий запуск. Никакого синхронного SQL диагностических счётчиков на тик.
Monitor jobs, полученные во время RECOVERING, диагностические: они не дают
исполнение после READY без нового авторизованного поколения/запуска проверки.
Свежие снимки после READY сохраняют прежние 5 с и прочие проверки маршрута.
При RECOVERING недостоверное исполнение PAPER не подставляется даже для SELL;
это может продлить открытый остаток. Мониторинг и исходный SELL продолжаются.
Guard не устраняет недостаток ликвидности и не создаёт выручку из остатка.

ДИАГНОСТИКА
app/data/clean_0762_recovery_v75.json: state, session, epoch, barrier times,
причина, time_pass, connection_epoch, market_mono, результат time_check,
последние 32 события RECOVERY_BEGIN / NEW_CONNECTION / TIME_RECHECK /
RECOVERY_READY / RECOVERY_STOP. Файл входит в 05_RESULTS и сохранение app/data.
Результаты допуска содержат RECOVERY_BLOCKED / PREFLIGHT_RECOVERY_INVALIDATED /
RECOVERY_INVALIDATED. input_json проверки и snapshot BUY сохраняют epoch.
Подробный time check остаётся в time_check_history с собственным ID.

ПРОВЕРКИ
Контролируемый PAPER-сценарий моделирует паузу 230 с и разрыв времени -4.259 с.
Немедленный BUY блокируется без изменения cash/positions; старая заявка не
исполняется после READY; новый BUY после полного допуска проходит и сохраняет
финансовую сверку. Отдельно проверены новый preflight, запрет старого результата
выхода, старого PASS, неизвестного состояния, отсутствие свежего тика,
повторный скачок и запрос восстановления от клиента.
Это инъекция времени в тесте, не реальное усыпление Windows и не доказательство
первопричины паузы прошлого запуска. Новый код не управляет sleep/clock ОС.

ЗАПУСК
Новая папка: 01_INSTALL → 02_SETTINGS → 04_CHECK → 03_START.
04_CHECK включает контролируемые PAPER-тесты нового допуска.
Панель http://127.0.0.1:8188. Старые базы/.env/.venv/код не переносить.
Короткий Windows-тест 20–30 минут; не создавать паузу вручную изменением часов.
При самопроизвольной паузе смотрим RECOVERY_BEGIN и условия нового READY.
Без такой паузы реальный путь восстановления не подтверждён; тесты уже
проверяют модель. При долгом RECOVERING сохранить отчёт, не ослаблять пороги.
Ctrl+C один раз, дождаться аудита завершения, затем 05_RESULTS.
При ошибке экспорта — 08_PRESERVE_DATA и сохранение monitor_evidence.
Базы прошлого теста остаются нетронутыми. AMM-экспорт v74 сохранён.
Прибыльность стратегии, сетевой AMM и Jito эта сборка не подтверждает.
