PUMPFUN BOT v0.7.67 — BUFFERED DIAGNOSTIC COUNTERS
Полная чистая PAPER-сборка. Пороги стратегии, watchdog и настройки часов сохранены.
Финансовые записи/транзакции и проверки свежести выхода сохранены.

ЧТО ИЗМЕНИЛОСЬ
candidate_lab.count и диагностический clock_lab.count больше не выполняют SQL
на каждом тике при запущенном боте. Они суммируют значения в ограниченном
словаре. Отдельный поток каждого сценария сохраняет пакет в SQLite не чаще
примерно двух раз в секунду. Свой SQLite connection используется только этим
потоком. Ни одна финансовая запись не проходит через этот буфер.

Две таблицы: candidate_counts_v0742 и clock_shadow_v0740. Не изменены функции
принятия событий/решений часов; перенесено только накопление счётчиков.
Остальные диагностические события, первые прохождения стадий и финансовые
операции сохраняют прежний путь. Выпуск устраняет конкретную синхронную запись
счётчика из зафиксированного стека, а не гарантирует отсутствие любых задержек.

ПРЕДЕЛЫ И ЧЕСТНЫЙ УЧЁТ
До 256 различных ключей в ожидающем буфере + до 256 в текущем пакете.
Повторы суммируются. Новый ключ при заполнении не блокирует тик: учитывается
как dropped. Пакет выполняется одной транзакцией; SQLITE_BUSY/LOCKED повторяется
только после rollback. Другие ошибки оставляют FAILED_UNFLUSHED, без возврата
к синхронному SQL в тике. В случае аварии несохранённые диагностические значения
могут потеряться; финансовый баланс этим не исправляется и не подменяется.
Счётчики описывают диагностические наблюдения и теперь отделены от транзакции
обрабатываемого тика; это не строго та же когорта, что подтверждённые сделки.

ИЗМЕРЕНИЯ
В 05_RESULTS и сохранении данных: *_counter_writer_v67.json для каждого процесса.
Есть session/PID, accepted, committed, dropped, unflushed, thread_alive и status.
Для последних 20 успешных пакетов и максимумов отдельно:
queue_ms — от первого накопленного значения до попытки;
begin_ms — получение write transaction (BEGIN IMMEDIATE);
write_ms — запись пакета;
commit_ms — commit.
last_error включает точный SQLite code/name, фазу, её длительность и очередь.
Повторные ожидания SQLITE_BUSY считаются busy_retries. Сохранённые показатели
не доказывают причину прошлой задержки SQLite или исправность накопителя.

ЗАВЕРШЕНИЕ
После отмены задач рынка выполняется попытка сброса буфера с ожиданием до 2 с
вне event loop. STOPPED + unflushed=0 + thread_alive=false подтверждают сброс.
STOPPED_UNFLUSHED/FAILED_UNFLUSHED или живой поток означают неполную диагностику.
Зависший ОС/SQLite поток нельзя безопасно убить; буфер остаётся ограниченным,
возврата к синхронным счётчикам нет. Это не финансовая транзакция.

ПРОВЕРКА НА WINDOWS
Старую папку и результаты сохранить. ZIP распаковать в новую папку:
01_INSTALL → 02_SETTINGS → 04_CHECK → 03_START; панель 8188, версия v0.7.67.
Не переносить старые app/data, .env, .venv или отдельные .py.
Короткий тест до 3–5 полных primary/ROUTE-пар либо 20–30 минут, раньше при ошибке.
Не ждать 100 сделок. Ctrl+C, дождаться завершения, 05_RESULTS; прислать оба архива.
Сравнить очередь/BEGIN/write/commit, dropped/unflushed и снимки watchdog.
Нативный Windows-прогон новой схемы ещё требуется. Локально есть тест удержания
write lock: тики event loop продолжаются, пакет не дублируется после retry.
Если экспорт повреждён — 08_PRESERVE_DATA из новой папки для остановленной старой
app/data. Исходники не ремонтируются. Старая причина повреждения не установлена.
Этот выпуск не подтверждает прибыльность, AMM-выход или Jito.
