Фаза 3 — отдельный CLI, не торговля из PAPER
- jito_execution.py использует существующие прямые Pump buy_v2/sell_v2, зашифрованный внешний vault, изолированный signer и единый журнал кошелька.
- Один bundle содержит одну подписанную транзакцию swap + SOL tip. Отдельной безусловной tip-транзакции нет: это рекомендованная Jito защита от раздельного rebroadcast в skipped/uncled block. Транспорт поддерживает до 5 транзакций, но торговый модуль намеренно отправляет одну.
- sendBundle использует base64 и явное encoding. Tip account выбирается случайно из проверенного getTipAccounts; список кэшируется до 60 с.
- Tip floor запрашивается через официальный REST Jito, не через несуществующий у Jito JSON-RPC getTipFloor. Доступны P75 (по умолчанию) и P95, округление вверх до lamports, минимум 1000, жёсткий cap. Будущие/старше 30 с/нечисловые значения отклоняются. QuickNode Lil JIT не подключён.
- Priority fee задаётся отдельно через priority_micro_lamports за CU. Пример 5000 при 200000 CU даёт 1000 lamports. Это отдельная плата от tip. fee_budget покрывает общий максимальный расход сверх BUY, включая tip, сеть и rent. Проверяются подпись, получатель tip, caps, баланс и подписанная симуляция sigVerify=true перед отправкой.
- Журнал фиксирует intent и подпись до сетевого отправления; UNKNOWN и истёкший blockhash оставляют кошелёк зарезервированным после перезапуска. Никакого fallback в обычный RPC после сомнительного sendBundle нет.
- getBundleStatuses проверяет bundle_id, точный список подписей и slot. getInflightBundleStatuses показывает Pending/Failed/Invalid/Landed. Подпись дополнительно проверяется в Solana: окончательный денежный учёт выполняется только по finalized metadata. Финализированная подпись при неизвестном bundle учитывается финансово, но не выдаётся за подтверждённый bundle landing.
- Два слота — критерий дополнительной диагностики, не доказательство неисполнения и не обещание 800 мс. При стандартном лимите Jito 1 запрос/с наблюдение двух API занимает дольше. Слоты измеряются RPC, не таймером 800 мс.
- Автоматическая пересборка разрешена только после явного Jito Failed (по документации: все регионы отказали, bundle не был forwarded), отсутствия landed bundle и подписи в сети. Pending/Invalid/null/таймаут/истечение blockhash не дают разрешения. Для отказа нужен наблюдаемый интервал >=2 слотов. После отказа заново читаются аккаунты, баланс и blockhash; требуется новый blockhash, tip увеличивается на 25% по умолчанию в пределах cap. Новый intent и подпись; старые байты не переотправляются. Лимит 1–3 попытки и circuit breaker действуют на каждую попытку.
- В 05_RESULTS execution_journal.zip содержит метаданные попыток, отдельно принятые ID, наблюдавшиеся landing, inclusion rate и неопределённые состояния. В denominator входят принятые ID и сомнительные отправки; это наблюдаемая доля с неполными данными, не гарантия сети. Vault, policy, пароль и подписанные байты не экспортируются. Журнал не содержит ключей, но содержит публичные адреса, подписи и денежные результаты.
- Отчёт выводит запрошенный tip и фактически уплаченный tip отдельно: finalized success — запрошенный tip; finalized failure — 0 (трансфер откатился), неизвестный исход — неизвестно. Фактические network fee и wallet delta берутся из сети.

Подготовка без отправки (из корня установленной папки)
Скопируйте app/research/phase3_plan.example.json за пределы папки бота, например C:\PumpfunBotPrivate\phase3_plan.json, и заполните RPC, полный genesis, публичный адрес, mint, количество/лимит и caps. Приватный ключ в план не помещать. risk_limits.day — текущая дата UTC. daily_start_equity_lamports — явно заданная стартовая сумма; пример 0 не разрешает отправку.
.venv\Scripts\python.exe app\jito_execution.py prepare --plan C:\PumpfunBotPrivate\phase3_plan.json
Команда читает сеть и tip floor, выдаёт текущие tip_accounts/расчёт, не подписывает и не отправляет. Signer policy должен разрешать mint, сумму, priority и выбранные проверенные tip accounts; policy по-прежнему отдельный защищённый файл.

Отдельные команды
begin-day --plan ПУТЬ : однократно инициализирует дневной риск в журнале.
send --plan ПУТЬ --broadcast : реальная отправка; пароль vault вводится getpass, не аргументом/из env. Без --broadcast отправки нет. Не запускайте эту команду для обычного PAPER-теста.
track --plan ПУТЬ --intent ID : продолжает только наблюдение существующего intent, не пересылает.
summary --plan ПУТЬ : локальная сводка журнала.
Все команды через .venv\Scripts\python.exe app\jito_execution.py ...
Если исход UNKNOWN, сначала track и разбор журналов; не удалять журнал и не создавать другой обходной журнал кошелька.
