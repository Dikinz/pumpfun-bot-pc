# Отдельное приложение для Windows вместо терминала в браузере — план

Только проект. Код не менялся. Версии внешних компонентов и правила подписи проверены на 02.11.2026.

## Что важно в текущей архитектуре

- **Процессы.** `03_START.bat` вызывает `.venv\Scripts\python.exe -I bootstrap.py start`, тот передаёт управление в `launcher.start()`. Лаунчер запускает отдельные процессы Python: панель, `main.py` (CTRL_BREAK), монитор (живёт, пока открыт его stdin) и ветку ROUTE. Каждый процесс запускается как `[sys.executable, '<скрипт>.py']`, поэтому «заморозить» движок в PyInstaller или Nuitka без переделки нельзя: в замороженной сборке `sys.executable` указывает на exe, а не на python.
- **Защита при старте.**
  - Окружение должно быть именно `ROOT/.venv`.
  - `release_guard` при каждом старте сверяет хеши файлов из `BUILD_MANIFEST.json`. Лишний `.py` в `app/` блокирует запуск.
  - Порты 8188 и 49190 должны быть свободны.
  - Повторный запуск блокирует lock-файл.

  Значит, установленное приложение — это то же дерево релиза с настоящим `.venv` внутри.
- **Остановка.** Сейчас бот останавливают через Ctrl+C в консоли. Лаунчер записывает стоп-запрос, шлёт боту CTRL_BREAK, по очереди останавливает ветки и монитор и затем проверяет закрытие SQLite. Для окна-оболочки уже есть готовый корректный путь: `launcher.start(stop_condition=...)`. Его использует 15_PAPER_FAULT_TEST, и он покрыт тестами. Оболочке нельзя просто «убить» лаунчер: тогда не выполнится корректная остановка.
- **Интерфейс.** Локальный HTTP-сервер на 127.0.0.1:8188 только читает данные (`/overview`, `/api`, `/health`). Терминал — один HTML без CDN. В окне WebView2 он работает без изменений.
- **Данные.** `app/data` (кампания), `app/.env` и `results/` должны переживать обновления. Новая версия ставится поверх старой с удалением старых `app/**/*.py`, но без удаления `app/data`.

## Варианты

| | Суть | Плюсы | Минусы | Срок MVP |
|---|---|---|---|---|
| **A. Окно WebView2 (pywebview) + трей + установщик** | Окно открывает `http://127.0.0.1:8188/`. Движок запускается как сейчас | Движок, тесты, `release_guard` и экспорт не меняются. WebView2 есть почти на всех Windows 10/11 | Совместимость pywebview с Python 3.14 нужно проверить: заявлена поддержка до 3.13, а pythonnet 3.2 поддерживает 3.11–3.15 | 4–6 дней |
| B. Tauri или Electron + Python как вспомогательный процесс | Оболочка на Rust или Node | Готовые автообновление и установщик | Документация Tauri рассчитана на движок, собранный PyInstaller, а с ним ломается `release_guard`. Новый язык. Electron весит больше 100 МБ | 7–12 дней |
| C. Нативный интерфейс на Qt (PySide6) | Переписать терминал | Полностью нативный интерфейс | Переписать около 62 КБ логики отображения. Интерфейс разойдётся с отчётами в results | 3–6 недель |
| D. Оболочка на C# (WinForms/WPF + WebView2) | Небольшой exe с окном и треем | Зрелые трей, Job Objects и подпись | Второй язык в проекте | 3–5 дней |

Общее для всех вариантов:
- **Движок не «замораживать».** Встроить полноценный CPython 3.14 и при установке собрать `.venv` из вложенных wheel-файлов с хешами.
- **Антивирусы.** Именно у PyInstaller-сборок часты ложные срабатывания, отказ от заморозки их снимает.
- **Подпись.** EV-сертификат больше не даёт мгновенной репутации в SmartScreen. Пока приложение собирается и ставится только у тебя, подпись можно отложить.
- **Установщик.** Inno Setup на пользователя, в `%LOCALAPPDATA%\Programs`, без прав администратора. MSIX и Program Files не подходят: `app/data` должна быть доступна на запись.
- **Как работает приложение.** Трей-приложение, не служба Windows. У службы нет консоли, поэтому не работает цепочка остановки, и ей нужны права администратора.
- **Обновления.** Только «проверить и уведомить», устанавливать вручную после остановки бота. Тихое обновление посреди кампании недопустимо.

## Рекомендация: вариант A, оболочка отделена от движка

**Главное правило:** закрытие или падение окна никогда не останавливает кампанию. Окно только показывает данные и управляет запуском. При перезапуске окно находит работающий бот по lock-файлу и `/health`.

1. **Спайк, 1 день, на тестовой копии, не на рабочей установке.**
   - Проверить pywebview + pythonnet на Python 3.14 в отдельном `.venv-ui`.
   - Открыть терминал с `?demo=1`.
   - Проверить трей и сохранение настроек вкладок.
   - Если не заработает, перейти на вариант D.
2. **MVP, 4–6 дней.**
   - Точка входа `app/desktop_host.py`: те же проверки, что в `bootstrap`, затем `launcher.start(stop_condition=<стоп-файл>)`. Браузер не открывается.
   - Кнопки:
     - «Остановить» — с подтверждением и прогрессом корректной остановки;
     - «Результаты» и «Проверка» — с выводом журнала в окно;
     - «Настройки» и «Сохранить данные» — открывают обычную консоль, потому что там ввод ключей через `getpass`.
   - Закрытие окна сворачивает приложение в трей.
3. **Установщик, 3–4 дня.**
   - Inno Setup, встроенный CPython, офлайн-wheel-файлы с хешами.
   - Обновление поверх с сохранением `app/data`, `.env` и `results`.
   - Ярлыки; установщик WebView2, если его нет.
4. **Дополнительно, 2–3 дня.** Уведомление об обновлениях, подпись, проверка заголовка `Host` на сервере панели, автозапуск (по умолчанию выключен).

Итого около 8–11 рабочих дней. Основные риски:
- работа pywebview на Python 3.14;
- остановка бота без видимой консоли;
- поведение при выходе из Windows: корректная остановка занимает больше 35 с.

## Что не меняется

- Только PAPER.
- Ключи кошелька в интерфейсе не вводятся и не показываются.
- API только читает данные и доступен только с 127.0.0.1.
- `release_guard` проверяет файлы при каждом старте.
- Путь к базе остаётся `app/data/clean_0762.db`.
- Корректная остановка и проверка закрытия SQLite остаются.
- Тесты и формат results остаются.
- Без прав администратора и без службы Windows.
