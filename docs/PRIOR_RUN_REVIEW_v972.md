## Найденный дефект выбора проверки

У остатка 23 проверки: 3 SELLABLE до сигнала, 3 DATA_REJECTED, 11 INSUFFICIENT_RESERVES, 6 WORKER_TIMEOUT. После сигнала отрицательные результаты и технические ошибки разделены явно.

Последовательность после сигнала:

1. +0,35 с: начата полная проверка, подтверждена нехватка резервов.
2. +10,39 с: лёгкая свежая проверка с одним RPC, нехватка подтверждена снова.
3. +20,47 с: лёгкая проверка получила локальную RPC-отсрочку.
4. +30,48 с: следующая проверка уже имеет `reserve_probe_v96: false` и запускает полный сценарий.
5. Затем шесть таймаутов по 10 с; после третьего подключается штатный backoff 30, 60, 120, 240 с.
6. Только +542,44 с снова начинается завершившаяся полная проверка, вновь подтверждающая нехватку резервов. После неё возвращаются лёгкие проверки.

Причина подтверждена исходным кодом v0.7.97.2: `position_monitor.next_job` выбирает последнее `result_json` и определяет `reserve_probe_v96` исключительно по его полю reserves. DATA_REJECTED не содержит reserves и стирает режим дешёвой проверки. Это дефект выбора следующего пути, а не доказательство исчезновения отрицательного состояния пула.

Всего в ROUTE записано 12 свежих отрицательных `CURVE_RESERVE_PROBE_INSUFFICIENT`, каждый с одним RPC; ещё 3 результата нехватки получены полной проверкой. Это подтверждает работу лёгкого пути, но не исправность выбора пути после технической ошибки.

В шести таймаутах CreateProcessW занимал около 143–203 мс; в сохранённых RPC-наблюдениях есть многосекундные запросы, включая getMultipleAccounts около 4,8–5,1 с. Все шесть завершений дочернего дерева подтверждены `CLEANUP_CONFIRMED`. Эти случаи не доказывают повтор прежнего 140-секундного зависания CreateProcessW. Точная транспортная причина медленных запросов не установлена.

Следующая правка: использовать последнее подтверждённое состояние нехватки резервов только как подсказку для выбора лёгкой проверки, сохраняя его через локальную отсрочку. Сами резервы каждый раз получать заново. При изменении поколения восстановления, маршрута или объёма учитывать новую идентичность задания; при восстановлении ликвидности выполнять полный свежий захват и симуляцию. Общий RPC-лимит, свежесть, Retry-After и правила подтверждения выхода сохранять.

У 10 закрытых ROUTE-сделок сигнал → закрытие: **4,20–45,21 с**, медиана **5,14 с**. Самый долгий выход включал четыре отрицательные проверки резервов до успешной продажи. Выборка отличается от предыдущих прогонов, поэтому снижение медианы не доказывает устойчивое ускорение.
