# ТЗ: PAPER-стратегия входа после миграции в PumpSwap AMM (AMM_STRATEGY_V1)

Статус: проект, реализации нет. База: v0.7.101.6 (ветка после прогона 02.11.2026).
Только PAPER: нет подписи, нет отправки транзакций, нет приватных ключей. Все пороги ниже — гипотезы
для первой выборки, а не найденные оптимумы.

## 0. Кратко

- Новая независимая ветка `amm_strategy_branch`: сама находит токены, перешедшие с кривой pump.fun
  в пул PumpSwap, сама входит, сама выходит. Не копирует входы PRIMARY (в отличие от `paper_branch`
  и `route_branch`).
- Свой файл БД `<primary>_amm_strategy.db`, своя выборка, свой капитал. Ни одно закрытие не попадает
  в выборку этапа 2 PRIMARY (59/100, пороги заморожены).
- Вход и выход подтверждаются изолированной локальной симуляцией PumpSwap на свежем снимке пула
  (как проверенный выход ROUTE). Тикового запасного выхода в учёте нет.
- По умолчанию выключено (`AMM_STRATEGY_MODE=off`). Порядок: shadow-сигналы → PAPER-входы → разбор
  после 100 закрытий.
- Главный недостающий кусок — лента данных: PumpApi-сообщения из AMM-пулов сейчас отбрасываются
  в `app/main.py:1280`, события миграции не принимаются нигде, симуляции покупки в AMM нет.

## 1. Цель и гипотеза

### 1.1 Почему отдельная стратегия

Текущая AMM-ветка (`app/paper_branch.py`, `AMM_BRANCH_ENABLED=0`, `app/config.py:383`) своих входов
не имеет: копирует BUY PRIMARY через `app/shared_lots.py` и проверяет AMM-выход, только если токен
мигрировал за время удержания PRIMARY (≤120 с, `MAX_HOLD`, `app/config.py:29`). На практике это
не происходит: прогон 02.11.2026 (v0.7.101.5) — 0 AMM-выходов; trial `amm_signal_exit` — 59 входов,
59 тиковых fallback, 0 локальных AMM-выходов. Пункт «Проверенный AMM-выход» в
`app/roadmap_progress.py:33` поэтому не закрывается. Стратегия, которая входит уже после миграции,
впервые даёт AMM-выходы в достаточном количестве и проверяет отдельную рыночную гипотезу.

### 1.2 Гипотеза H1

Токены, которые завершили кривую и перешли в PumpSwap, в первые минуты после миграции при
подтверждённой ликвидности пула и продолжающемся притоке покупок дают положительное математическое
ожидание сделки после всех учтённых расходов при фиксированных правилах входа/выхода из разделов 4–5.

Нулевая гипотеза H0: средний чистый результат на сделку ≤ 0 (стратегия не лучше «ничего не делать»).

### 1.3 Почему проверка объективна

1. **Свои входы.** Сигнал строит только ветка по своим данным. PRIMARY и ROUTE не влияют на выбор.
2. **Своя выборка.** Отдельная БД, отдельный счётчик закрытий, отдельный стартовый капитал.
   В `campaign_view` и `roadmap_progress` роль `amm_strategy`, а не `amm`, поэтому закрытия не
   попадают в `closed` этапа 2 (см. `app/campaign_view.py:121-122`, где `role=='amm'` служит fallback).
3. **Замороженные правила.** Все пороги лежат в словаре `RULES` с sha256 и записываются в БД при
   первом запуске, как в `app/exit_rules_v33.py:15-22` (`RULES_CHANGED_START_NEW_TEST_DATABASE`).
   Любое изменение порога — новая БД и новая выборка с нуля.
4. **Две базы сравнения, раздельно:**
   - **B0, «ничего не делать»:** результат 0 PAPER, без расходов. Стратегия должна быть строго лучше
     с учётом расходов и открытых остатков по стрессовой оценке (раздел 8.3).
   - **B1, «без фильтров»:** shadow-когорта. Каждый подтверждённый мигрировавший токен, прошедший
     только технические проверки (E8, E13), получает виртуальный вход в момент `age=E1.min` и выход
     по тем же правилам выхода. Оценка по цене ленты (`TICK_SHADOW_NOT_LEDGER`), без RPC. Показывает,
     добавляют ли фильтры E2–E7 ценность, или результат даёт сам факт миграции.
   - **PRIMARY показывается рядом, но никогда не складывается** с AMM-стратегией: другие токены,
     другое время жизни, другая модель расходов.
5. **Проверенное исполнение.** Учёт ведётся только по успешной изолированной симуляции покупки и
   продажи на свежем канонически проверенном пуле. Непроверенный выход — открытый остаток, а не цена тика.

## 3. Источники данных

### 3.1 Откуда сейчас идут рыночные данные

- **Обнаружение токенов:** PumpPortal `wss://pumpportal.fun/api/data`, только `subscribeNewToken`
  (`app/main.py:1031-1037`). Сообщения о миграции не запрашиваются.
- **Сделки:** по умолчанию PumpApi `wss://stream.pumpapi.io/` (`app/config.py:78`,
  `app/main.py:1210-1306`). Подписка не отправляется, поток общий по всему рынку. Каждое сообщение
  несёт поле `pool`. Всё, что не `PUMPAPI_POOL='pump'` (`app/config.py:79`), отбрасывается
  в `app/main.py:1280-1282`; для открытых позиций PRIMARY пишется только диагностика `OTHER_POOL`.
  Сообщения с `action` не из `buy/sell` отбрасываются в `app/main.py:1279`.
- **Ветки получают поток** через `branch_transport.emit()` только для mint из открытых позиций ветки
  (`app/main.py:1297-1299`, `app/branch_transport.py:200`). Проверка пула стоит раньше, поэтому
  AMM-сделки до веток не доходят никогда.
- **Свежесть цены для исполнения PRIMARY:** `app/execution_model.py:24-31` требует `pool=='pump'`,
  `MAX_PRICE_AGE=1.0` с (`:10`). Для AMM-сделок этот код не подходит без изменения, поэтому
  стратегия получает свою проверку свежести, а `execution_model` PRIMARY не меняется.

### 3.2 Детекция миграции

Событие миграции фиксируется как `MIGRATION_OBSERVED` с указанием источника, затем обязательно
подтверждается RPC (`MIGRATION_CONFIRMED`). Без подтверждения вход невозможен.

| Вариант | Источник | RPC | Статус |
|---|---|---|---|
| A (основной) | Первое сообщение PumpApi по mint с `pool` из множества AMM-меток | 0 | Нужно добавить пересылку (см. 3.4). Точное значение метки AMM-пула в PumpApi в репозитории не подтверждено: в тестах встречается только `'pumpswap'` (`app/tests/test_diagnostics.py:29`) как пример. Метку и наличие отдельного события миграции (`action` не buy/sell) установить на этапе S0 по счётчикам |
| B (дополнительный) | PumpPortal `subscribeMigration` на уже открытом сокете обнаружения (`app/main.py:1037`), без нового соединения | 0 | По документации провайдера; в коде не проверялось. Включается флагом, только если A недостаточен |
| C (резерв) | Опрос флага `complete` (`raw[48]`) у кривых из списка наблюдения пакетами `getMultipleAccounts` ≤100 адресов | ≤0.1 запр./с | Только если A и B не работают. Список наблюдения — mint с ценой/прогрессом кривой выше порога (порог измерить на S0) |
| Подтверждение | `amm.canonical(mint)` + чтение пула, `names_for()` | 1 запрос на mint | Обязательно. Результат: `CONFIRMED` / `AMM_POOL_NOT_FOUND` / `AMM_POOL_FEATURE_UNSUPPORTED` и т.д. |

Время миграции `migration_ts` = время первого наблюдения (`first_seen_ts`), источник пишется в
`migration_ts_source` (`PROVIDER_EVENT`, `FIRST_AMM_TRADE`, `CURVE_COMPLETE_POLL`). Погрешность
для C — до интервала опроса; поэтому окно E1 начинается не с нуля.

### 3.3 Лента цены и объёма AMM, правила свежести

Источник — те же сообщения PumpApi (вариант A), пересланные в ветку. Поля: `mint`, `action`,
`price` (или `quoteAmount/tokenAmount`), `txSigner`, `timestamp`, `signature`, `quoteMint`,
`poolFeeRate` (см. разбор в `app/cost_evidence.py:35-50`).

Правила свежести (технические, не настраиваются в выборке):

- F1. Сообщение принимается, если `quoteMint` = SOL, `signature` не пустая, `clock_status='OK'`,
  `0 ≤ provider_lag_ms ≤ 1000`.
- F2. Для решения о входе последняя сделка mint не старше 5 с, а общий AMM-поток не молчит дольше 10 с.
- F3. Для сигнала выхода цена не старше 5 с; иначе сигнал не строится, а через 30 с без свежей цены
  срабатывает X6 (`DATA_GAP`).
- F4. Перед входом цена ленты сверяется с ценой снимка пула: `|p_stream / p_snapshot − 1| ≤ 5 %`,
  иначе `STREAM_SNAPSHOT_MISMATCH`. Основа цены AMM-сообщений PumpApi не подтверждена — F4 её проверяет.
- F5. Разрыв входного потока ветки (`branch_input_gap`, как в `app/paper_branch.py`) блокирует новые
  входы до конца сессии, выходы продолжают работать по RPC.

### 3.4 Чего не хватает в текущем коде

1. **Пересылка AMM-сообщений.** В `app/main.py:1280` перед `continue` нужен O(1)-вызов
   `branch_transport.emit_amm(x, now, recv_mono)` для `pool ∈ AMM_POOL_LABELS`. Отдаётся только
   publisher-у с `wants_amm=True`; `Fanout.emit` (`app/branch_transport.py:219`) остальным веткам
   не меняется. Поведение PRIMARY неизменно (`continue` остаётся).
2. **Отдельная очередь.** У AMM-publisher своя `queue.Queue` (как `maxsize=2000`, `:62`), свои счётчики
   `dropped`. Переполнение не должно выставлять разрыв PRIMARY/ROUTE.
3. **Счётчики S0 без логики:** число сообщений по каждому значению `pool` и `action` в минуту
   (`stream_pool_labels_v1`), чтобы установить метку AMM и наличие события миграции.
4. **Трекер миграций** (`amm_feed.MigrationTracker`): первое наблюдение, подтверждение, окно E1.
5. **Симуляция покупки в AMM.** В `app/amm_simulation.py` есть только `sell_v2` (`:160`). Нужна
   `run_buy_snapshot(bundle, quote_in)` через `buy_exact_quote_in_v2` (есть в IDL
   `app/research/pump_amm_idl_v36.json`), та же схема проверок и отрицательный контроль
   (покупка с нулевым SOL должна упасть).
6. **Лёгкий зонд резервов** `amm_reserve_probe` (1 запрос `getMultipleAccounts`: пул + 2 хранилища),
   по образцу `app/curve_reserve_probe_v96.py`, для X5 и E2 без полного снимка программ.
7. **Модель кошелька для AMM.** `route_branch.wallet_account` (`app/route_branch.py:35-51`) рассчитан
   на поля кривой (`seller_net_lamports`, `token_rent_lamports`); для AMM-продажи
   (`base_account_rent_lamports`, `quote_account_rent_lamports`, `volume_rent_delta_lamports`) нужен
   свой вариант (раздел 6).
8. **Собственная (не копирующая) БД.** `paper_branch.seed` копирует БД PRIMARY целиком
   (`app/paper_branch.py:51`, `src.backup`); для независимой выборки нужна пустая БД со ссылкой
   `source_identity` на PRIMARY.
9. **Наборы веток.** `branch_plan_v101.NAMES` и проверка `modules not in (...)`
   (`app/branch_plan_v101.py:4,27`) и `branch_mode_v100.modules()` знают только
   `paper_branch` и `route_branch`.

### 3.5 Бюджет RPC

Общий лимит не меняется: 6 запросов/с на origin, не более 4 в полёте (`app/rpc_budget.py:151`,
`app/config.py:372-373`). У стратегии свой потолок внутри общего: среднее ≤1 запрос/с, ≤1 в полёте,
фоновый приоритет. `AMM_STRATEGY_RPC_RATE` проверяется при старте: `0 < x ≤ 1` и
`x ≤ RPC_MAX_REQUESTS_PER_SECOND`, иначе отказ запуска. Проверки выхода стратегии идут через
`rpc_priority.exit_check` (у PRIMARY/ROUTE тот же механизм, лимит аренд 16, `app/rpc_priority.py:12`).

| Операция | Запросов | Частота (оценка) | Средняя нагрузка |
|---|---|---|---|
| Подтверждение миграции | 1 | N_mig в час (измерить на S0; для оценки 30/ч) | ≈0.01/с |
| Снимок для входа (`capture`: discovery + accounts + bank с кэшем программ) | 3–4 | ≤6 входов/ч (E12) + отказы на снимке ≤20/ч | ≈0.02/с |
| Зонд резервов открытой позиции | 1 | раз в 15 с × ≤2 позиции | ≈0.13/с |
| Проверка выхода (снимок + продажа + контроль) | 3–4 | после сигнала, повтор раз в 10 с до успеха | пик ≈0.4/с на позицию |
| Вариант C (если включён) | 1 на 100 mint | раз в 10 с | 0.1/с |

Итог: ≤0.3 запр./с в среднем, пики до 1 запр./с. Если общий контроль отвечает `RATE`/`COOLDOWN`,
стратегия откладывает вход (`RPC_DEFERRED`) и не ставит новых заданий; на PRIMARY это не влияет.

## 4. Правила входа (гипотезы первой выборки)

Все значения записываются в `RULES` и замораживаются. «Тех.» — техническое правило, не является
параметром стратегии, но тоже не меняется в течение выборки.

| Код | Правило | Стартовое значение | Тип |
|---|---|---|---|

| E6 | Импульс: цена сейчас ≥ цены 30 с назад | ≥ 0 % | гипотеза |

Порядок проверки: сначала дешёвые E1, E3–E7, E9 (по ленте), затем подтверждение пула (E2, E8) одним
запросом, в конце снимок и симуляция покупки E10. Каждое решение пишется в `amm_signals_v1` с кодом
первой нарушенной проверки — это и есть shadow-набор этапа S1 и когорта B1.

Вход в учёт: `BUY` фиксируется по результату симуляции — `tokens_credited` (сырые единицы),
`quote_spent_lamports`, расходы (раздел 6), курс SOL/PAPER из `exit_quotes.FX` в момент снимка
(замораживается для сделки, как `inventory.sol_usdc` в `app/amm_exit_scenario.py:212`).

## 5. Правила выхода и проверка исполнения

### 5.1 Сигналы (по ленте, гипотезы)

`mark` — чистая оценка позиции: `p_stream × tokens × (1 − fee_bps_snapshot/10⁴)` минус ожидаемые
фиксированные расходы выхода, в PAPER по курсу входа; доход считается к полной стоимости входа.

| Код | Условие | Стартовое значение |
|---|---|---|
| X1 SL | `mark_pnl ≤ −10 %` | −10 % |
| X2 TP | `mark_pnl ≥ +25 %`, выход целиком (частичных выходов нет: симуляция продаёт весь объём) | +25 % |
| X3 Trailing | Включается при `mark_pnl ≥ +12 %`; выход при падении `mark` на 7 % от максимума | +12 % / 7 % |
| X4 Max hold | Возраст позиции ≥ 600 с | 600 с |
| X5 Ликвидность | Зонд резервов: `effective_quote < 70 %` от снимка входа | 70 % |
| X6 Нет данных | Нет свежей цены mint 30 с (F3) | 30 с |

Сигналы пишутся в `paper_orders`-подобную таблицу со статусом `PENDING` (как SELL PENDING у ROUTE,
`app/route_branch.py:26-30`). Одновременно может быть один сигнал на позицию; первый сработавший
код сохраняется как `reason`.

### 5.2 Проверенный выход

1. После сигнала ставится задание `route='PUMP_AMM'`, `priority_exit=True`, `scheduled_ts ≥ signal_ts`.
2. Дочерний процесс `position_monitor.launch_check` (`app/position_monitor.py:328`) выполняет
   `amm_experiment` (`:210`): свежий `capture`, `run_snapshot` на точный сырой объём позиции и
   отрицательный контроль.
3. Решение `amm_strategy.assess_exit()` по правилам `app/amm_exit_scenario.py:191-241`: снимок ≤5 с,
   проверка ≤25 с от планирования, канонический пул, `AMM_SALE_EXECUTED`, совпадение объёма
   (`raw_amount = tokens_debited = pool_tokens_credited`), согласованность учёта
   (`net = credit + delta − base − quote`, `delta = −(fee + volume + topup)`), изоляция
   (`broadcast=False`, `paper_mutated=False`). Повторная проверка свежести в момент записи, как
   `app/route_branch.py:114-118`.
4. Успех → `SELL` с `rate_source='AMM_STRATEGY_VERIFIED_ISOLATED'`, слот освобождается.
5. Неуспех → сигнал остаётся `PENDING`, повтор через 10 с. **Тикового fallback в учёте нет.**
   `AMM_INSUFFICIENT_RESERVES` и неподдерживаемый пул — открытый остаток. Через 30 мин без проверенного
   выхода позиция получает метку `STUCK_UNVERIFIED` и в стрессовой оценке капитала стоит 0.
6. Для отчёта рядом пишется `tick_shadow_receipt` с меткой `TICK_SHADOW_NOT_LEDGER`: что дал бы тик.
   В капитал, PnL и выборку это значение не входит.

## 6. Модель расходов (`AMM_STRATEGY_WALLET_MODEL_V1`)

Принцип как у `ROUTE_WALLET_MODEL_V1016` (`app/route_branch.py:32-51`): один постоянный PAPER-кошелёк,
строгие изолированные значения сохраняются в `strict_*` для отчёта чувствительности.

| Статья | Откуда | Статус |
|---|---|---|
| Комиссии пула PumpSwap (LP, протокол, создатель монеты, buyback) | Исполняются программой внутри симуляции; уже в `quote_received` / `quote_spent`. Ставки для отчёта читать из `GlobalConfig` (`lp_fee_basis_points`, `protocol_fee_basis_points`, `coin_creator_fee_basis_points`, `buyback_basis_points`) и `FeeConfig.fee_tiers` по капитализации | Измеряется. Ставки в коде не задаются; публичные значения ≈0.25–0.30 % — только ориентир |
| Пулы с `creator_fee_bps≠0`, mayhem, cashback, holder_reward | Отклоняются `names_for()` (`app/amm_simulation.py:76`) | Не торгуются; доля отказов в отчёте |
| Аренда токен-счёта (ATA базового токена) | Платится при BUY (`base_account_rent_lamports`), возвращается при закрытии пустого счёта минус комиссия закрытия 5000 лампортов (`CLOSE_FEE_LAMPORTS`, `app/route_branch.py:33`) | Моделируется; возврат не доказан в сети |
| Временный WSOL-счёт | Создаётся и закрывается в той же транзакции; в симуляции `quote_account_rent_lamports` | Моделируется как возвращённый |
| `user_volume_accumulator` | Аренда платится первой операцией кошелька, дальше сохраняется (логика `retained` из `route_branch.wallet_account`) | Моделируется |
| Доплата аренды пула | `pool_rent_topup_lamports`, уже в дельте кошелька | Измеряется |
| Базовая комиссия подписи | `local_fee_lamports` из симуляции (BUY и SELL) | Измеряется локально |
| Priority fee, Jito, неудачные транзакции, задержка landing | Неизвестно. Покрывается сценарным бюджетом `fixed_per_fill = 0.005` PAPER на исполнение (`app/paper_capital.py:10`) | **НЕИЗВЕСТНО**, отдельной строкой |
| Плата сервиса маршрутизации | Прямой PumpSwap без агрегатора; для сравнимости с PRIMARY строка `route_rate = 0.0025` сохраняется, отчёт показывает чувствительность с 0 | Сценарий |
| Курс SOL/PAPER | Фиксируется на входе для сделки | Принято |

Формулы (лампорты, затем перевод по курсу входа):

- BUY: `entry_cost = quote_spent + base_rent + local_fee_buy + volume_rent(первый раз) + topup_buy`;
  `size = 3 PAPER` переводится в `quote_in` для `buy_exact_quote_in_v2`.
- SELL: `receipt = quote_received − local_fee_sell − topup_sell + base_rent − 5000`.
- `pnl = receipt·fx − size − entry_costs_paper − fixed_per_fill·2 − route_rate·(size + receipt·fx)`.

Строгий вариант (`strict_*`): каждая продажа как первая в новом кошельке, без возврата аренды —
как сейчас в `amm_exit_scenario`. Отчёт показывает оба; вывод делается по основному, если знак
результата совпадает, иначе — «зависит от модели кошелька».

## 10. Риски и открытые вопросы

**Риски**

1. Метка AMM-пула и основа цены в PumpApi не подтверждены (3.2, F4). Митигация: S0 и сверка F4.
2. Объём AMM-сообщений в общем потоке может нагрузить горячий путь PRIMARY. Митигация: O(1)
   фильтр, отдельная очередь, контроль `event_loop_lag_ms`, ограничение памяти в `amm_feed`.
3. Rug / вывод ликвидности сразу после миграции: X5 по зонду с шагом 15 с может опоздать.
   Остаток остаётся открытым и в стрессовой оценке стоит 0.
4. Неподдерживаемые пулы (`AMM_POOL_FEATURE_UNSUPPORTED`, Token-2022 с расширениями) сужают
   выборку и смещают её; доля отказов обязательна в отчёте.
5. Изменение программы PumpSwap или layout: `decode()` падает с `AMM_UNSUPPORTED_LAYOUT` /
   `AMM_UNKNOWN_EXTENSION` (`app/amm_simulation.py:42,49`) — вход невозможен, выходы остаются
   открытыми; при массовых отказах стратегия ставит `PAUSED_LAYOUT` и не открывает новые позиции.
6. Симуляция не учитывает конкуренцию за блок и MEV: исполнение в сети не доказано
   (`mainnet_execution_proven=False`).
7. Выживаемость: в выборку входят только токены, дошедшие до миграции, и только поддерживаемые пулы;
   выводы не переносятся на кривую PRIMARY.

**Открытые вопросы**

1. Точное значение `pool` для PumpSwap в PumpApi и есть ли отдельное сообщение миграции.
2. Нужен ли вариант B (PumpPortal `subscribeMigration`) и не нарушает ли он правило одного
   соединения провайдера.
3. Сколько миграций в час на самом деле; хватит ли их на 100 закрытий за разумный срок
   (при 5 входах в сутки — около 20 дней).
4. Какая доля комиссий пула применяется в первые минуты (`FeeConfig.fee_tiers` по капитализации).
5. Можно ли засчитывать проверенный AMM-выход стратегии в пункт этапа 1 roadmap — решение владельца.
6. Нужно ли ограничение суммарного открытого риска стратегии в дополнение к 2 позициям
   (например, остановка новых входов при `STUCK_UNVERIFIED ≥ 2`).
