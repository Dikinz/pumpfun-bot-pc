# Регрессия отмены после SAVE_RESULT

Источник: проверка a71137653b194406a834ecca16462295 в архиве v78.
После SAVE_RESULT процесс остался жив, отмена новым SELL завершилась
SIMULATION_CHILD_CLEANUP_TIMEOUT; аудит оставил PID 30056 STILL_RUNNING.

## Сценарий
1. Временная БД: позиция 3 PAPER и согласованный финансовый ledger.
2. Настоящий pm.run_job запускает BackgroundChild; записаны result.json и
   progress SAVE_RESULT. Задание ещё RUNNING, launcher/worker не завершились.
3. В БД появляется новый SELL; priority_exit.observe/preempt вызывает отмену.
4. Ожидается SUPERSEDED_BY_EXIT_SIGNAL и подтверждённая очистка всей группы.
5. В базе нет SELL-fill: сохранённый результат не используется. Капитал, резерв,
   открытая позиция и расходы не изменяются. Просроченная рыночная оценка может
   стать неизвестной — её не фиксируют искусственно свежей ради теста.
6. Новая проверка получает другой ID и старт после SELL. Неисполненная позиция
   не исчезает из учёта. Снимки дерева и integrity_check сохраняются до/после.

На Windows используется настоящий Job Object и wrapper, запускающий worker.
На Linux — явно помеченная модель. Модель отказа завершения должна привести к
CLEANUP_FAILED без CLEANUP_CONFIRMED. Это ожидаемый отрицательный контроль:
его ошибка в деталях отчёта не означает провал теста, если проверки PASSED.

Поле saved_result_cancel_windows_verified_v80=true возможно только на Windows
Python 3.14 после успешного native-сценария. Linux PASS этого не доказывает.
Двухчасовая приёмка остаётся заблокированной до успешного точного сценария.
Не увеличивать бюджеты очистки и не использовать SAVE_RESULT как подтверждение
завершения процесса. Реальная первопричина Windows-таймаута не установлена.
