# Разбор стратегии, риск-менеджмента, скорости и мусора — 01.11.2026

Источник: группа из 4 агентов-аналитиков, к каждому — независимый критик. Данные: два PAPER-прогона 01.11.2026. Run A (v0.7.101.1): 11 сделок. Run B (v0.7.101.2): 5 сделок. Агенты работали только на чтение с копиями баз; репозиторий, папка пользователя и сеть не затрагивались. Ниже — выводы с поправками критиков. Утверждения, которые критики не подтвердили, отмечены или убраны.

**Главная оговорка: 16 сделок — очень маленькая выборка. Это направления для проверки, а не доказанные свойства стратегии.**

## 1. Откуда убыток

| | Сумма |
|---|---|
| Валовый результат (gross) | −6.106 |
| Издержки | 1.508 |
| Чистый (net) | **−7.615** (A −5.866, B −1.748) |
| Прибыльных | 4 из 16; значимых 3 (одна +0.001) |

- **Три обвала дают 71% убытка.** Сделки BtAkqm, 4DCNBq и 6Ug9Up дали −5.425 net. Все три в Run A. Сценарий одинаковый: рост на +10…+17%, затем за одно окно исполнения цена падает на 55–60%, к уровню старта кривой pump.fun. Стоп или фиксация прибыли срабатывает, но исполняется уже по дну. Худшая сделка: сигнал PP на +7%, через 166 мс исполнение на −59%. ROUTE-ветка считает выход по состоянию кривой и показывает те же потери. Значит, обвалы реальные, а не ошибка модели.
- **Без обвалов** 13 сделок дают net −2.19: gross −0.90, издержки 1.29.
- **Издержки** — около 0.094 на круг, 3.1% позиции: пул 1.25%×2, маршрут 0.25%×2, фикс. 0.005×2. Чтобы выйти в ноль, нужно не меньше +3.4% gross на сделку. Сейчас в среднем −12.7%, без обвалов −2.3%. Издержки на кривой почти не сократить, улучшать нужно отбор и выходы.
- **Вход не виноват.** Preflight занимает около 2.8 с (медиана), ожидание исполнения около 0.7 с. Цена входа в среднем на 0.27% лучше цены сигнала. Ускорение входа прибыльности не даст.
- **ROUTE хуже PRIMARY почти только из-за ренты.** В Run A разница 3.40, из неё 2.96 — разовая рента аккаунтов (~0.27 на продажу). Исполнение тут ни при чём.

## 2. Что показывают отсеянные кандидаты (360 токенов, на тех же данных)

- **Anti-FOMO `MOMENTUM_HOT` отсекает худших.** У заблокированных медианное изменение цены через 30 с −21.6%, у прошедших фильтры −2.8%. Через 120 с: −46.6% против −11.3%. Ослаблять фильтр не нужно.
- **Множитель цены x = цена / стартовая цена кривой** связан с частотой обвалов. Среди прошедших фильтры падение на 30% и больше к 30 с случается у 6% при x<1.5 и примерно у 50% при x≥1.5. Но поправка критика: средний результат через 120 с от x почти не зависит (−8.0% против −7.4%). Лучшая сделка (+0.82) вошла при том же x≈2.55, что и обвалы. Значит, x — это фактор хвостового риска, а не доказанный фактор ожидаемой доходности. Пороги 1.5 и 2.0 подобраны после просмотра данных.
- Кандидаты, отсеянные preflight, через 2–5 минут вели себя не хуже вошедших. Причина отказа `PRICE_MOVED` встречается редко.

## 3. Гипотезы для повышения прибыльности

Все проверяются **в тени или в параллельной ветке**, без изменения порогов основной выборки из 100 сделок.

| № | Гипотеза | Что показали данные | Как проверить |
|---|---|---|---|
| H1 | Ранняя фиксация прибыли (TP +8%) или короткий трейл (вооружение +6%, откат 3%) | Офлайн net улучшается с −7.6 до −2.2…−2.7, но весь выигрыш даёт перехват трёх обвалов; на остальных 13 сделках около −0.3. ДИ 95% [−0.26; +11.9]. Результат немонотонен: TP10 даёт меньше. Модель исполнения через 250 мс оптимистичнее реальной медианы SELL 1.18 с | Теневые варианты выхода на каждой реальной позиции, исполнение по следующему тику с реальной задержкой. Нужно около 55 пар для эффекта +0.3 на сделку, около 220 для +0.15 |
| H2 | Учитывать x на входе | Связь с частотой обвалов сильная (p≈1e-10 по когортам), с ожиданием — нет | Только записывать x и метку «был бы заблокирован». Это делается **отдельной функцией журнала**, а не через `entry_quality`: там метки WOULD_BLOCK превращаются в настоящие блокировки (`ENTRY_QUALITY_V2`). Не меньше 150 прошедших фильтры, из них не меньше 40 с x≥1.5 |
| H3 | Размер позиции в зависимости от x | Подогнано на тех же 3 сделках | Только параллельная PAPER-ветка, не меньше 50 сделок |
| H4 | Тайм-стоп для «не пошедших» (10–20 с при минусе) | Эффект слабый (+0.8…+1.0 на 16 сделках) | Низкий приоритет, в том же теневом наборе |
| R0 | Записывать полные тиковые пути кандидатов PASS (300 с) | Сейчас таблица events пуста, сырые события выключены | Основа для всех офлайн-проверок. Сначала оценить нагрузку CPU и объём записи. Использовать существующие виртуальные позиции (`shadow_ab`, `exit_comparison`) |

Вывод: на текущих данных прибыльной конфигурации не видно. Даже лучший вариант выхода оставляет стратегию в минусе. Ближайшая полезная работа — собрать данные для этих проверок, не трогая основную выборку.

## 4. Риск-менеджмент

Что есть сейчас:
- **Размер позиции**: фиксированный, 3 из 30 (10%).
- **Слоты**: 2.
- **Вход** запрещён, если после издержек денег меньше 3.1025.
- **Режим**: жёсткий запрет всего, кроме PAPER.
- **Стопы**: STOP_LOSS −12%, FAST_STOP, EARLY_FAIL, MAX_HOLD_WATCHDOG, фиксация прибыли PP_10_7.

До live подключить лимиты по-настоящему |

## 5. Скорость .bat и проверок

- **04_CHECK** занимает около 4.5–5.5 мин, почти всё время — тесты. Recovery-набор около 193 с, технический остаток около 77 с, сбор тестов 10–12 с, selftest монитора, verify и проверка часов вместе около 5–7 с. Импорт модулей — доли секунды. Панель отвечает через 1.2 с. verify хэширует 388 файлов за 0.3–0.5 с.
- **Медленные тесты не считают, а ждут** реальные 10-секундные дедлайны. Четыре самых тяжёлых модуля дают около 110 с по стене при 13 с CPU. Часть ожиданий сознательно оставлена реальной, чтобы проверять настоящий интервал. Менять это только поштучно и без ослабления.
- **Параллельный запуск отклонён.** Две параллельные дорожки в единственном опыте дали 283 с против 284 с последовательно. Четыре дорожки — два ложных падения тестов процессов Windows. pytest-xdist в окружении нет.
- **Чистка ускорения не даст**: большие файлы на старт почти не влияют (0.04–0.08 с).
- **05_RESULTS** сжимает одни и те же данные дважды, а упаковка томов квадратична по числу файлов. Реальный выигрыш на данных пользователя не измерен.

## 6. Мусор и рост данных

- В git были случайно закоммичены 5 обрезанных временных файлов `app/research/.*.json.XXXXXX`, 50.9 МБ (43% рабочего дерева). В ZIP они не попадали.
- В репозитории не было `.gitignore`, поэтому `app/data`, `app/.env`, `dist/` и `__pycache__` можно было закоммитить случайно.
- Около 20.8 МБ занимают старые доказательства в `validation/`, они только в репозитории. Из ZIP можно убрать ещё около 6.3 МБ: LINUX_RECOVERY, старые docs, review_input и blob-файлы monitor_evidence. Blob-файлы закреплены в манифесте, поэтому убирать их можно только вместе с правкой манифеста и проверкой старта.
- Два фикстура по 17 МБ почти совпадают, но на них ссылаются 10 тестовых модулей. Менять — только с проверкой исходного sha256.
- Пять модулей без ссылок из рабочего кода: `check_entry_selection`, `replay_existing_db`, `execution_summary`, `replay_research`, `threshold_lab`. Это решение владельца; `replay_existing_db` может пригодиться для теневых проверок.
- У пользователя без ограничений растут `results/`, папки evidence и журнал `*_monitor_activity.jsonl` (около 1.3 МБ/ч на файл, 95–98% — heartbeat). Компактный heartbeat выгоднее простой ротации. Автоматически ничего не удалять, пока собирается выборка.
