# v0.7.101.2 — исправления по Windows-запуску 01.11.2026

Только PAPER, панель 127.0.0.1:8188. Метка сборки `RUN_REVIEW_V1012` (прежняя: v0.7.101.1 / AGENT_REVIEW_V1011).

## Что показал запуск 01.11.2026 (v0.7.101.1, Windows 10, Python 3.14)

- Первая проверка восстановления прервана примерно на 36-й секунде (Ctrl+C в консоли, а не зависание: таймаут 600 с так рано сработать не мог). Архив `recovery_failure_v89_*` неполный, упавших тестов нет.
- Повторная проверка восстановления: PASS, 605 тестов за ~301 с, `native_windows_verified=true` (для v0.7.101.1).
- PAPER-запуск длился ~91 минуту (5465 с), а не 2 часа. Он завершился автоматической управляемой остановкой: основной цикл ~53 с ждал SQLite `COMMIT` в `clean_0762.db` (стек `hot_trade_tick → setmany → atomic → commit`). Первопричина не установлена. Потерь учёта нет: accepted=committed, dropped=0, целостность OK.
- При остановке ветка ROUTE получила STOP-файл примерно за 1,5 с до принудительного завершения. Бот и панель завершены принудительно, `writer_acks_complete=false`.
- Обе ветки: 11 входов и 11 закрытий, открытых позиций нет. PRIMARY: −5,866 PAPER (расходы 1,027), побед 3. ROUTE: −9,271 PAPER, побед 2. Модели расходов веток различаются.
- 11 выходов Curve, 0 выходов AMM. Лаборатория выхода по сигналу не дала ни одного результата: все 11 заданий отложены локальной очередью RPC.
- Прогресс дорожной карты 21,5 %. Этап 1 — 80 % (не выполнен только пункт AMM-выхода), этап 2 — 6 %.
- Журнал диагностики системы ротировался: сохранилось только около 64 последних минут.

Это результаты стратегии и рынка на малой выборке (11 из 100). Пороги они не меняют.

## Исправления (регрессии в `app/tests/test_win314_run20261101.py`, 31 тест, входит в 04_CHECK)

- Проверка восстановления: перед стартом печатается предупреждение (обычно 4–5 минут, бюджет 600 с, Ctrl+C не нажимать), затем каждые 20 с строка прогресса. Прерывание Ctrl+C записывается в отчёт и архив как `INTERRUPTED`. Новый маркер `results/recovery_last_attempt_v89.json` хранит итог последней попытки. Прерванная попытка не стирает прежний PASS, а экспорт предупреждает, если прерывание было позже него.
- Зависание основного цикла: перед остановкой сохраняется `*_stall_evidence_v1012.json` (размеры и время DB/WAL/SHM, CPU и I/O процессов и потоков, стеки всех потоков, текущий SQL). Файл попадает в 05_RESULTS и 08_PRESERVE_DATA. Настройки SQLite (checkpoint/WAL) не менялись: причина не доказана.
- Остановка при зависшем основном процессе: launcher сам пишет STOP-файлы веток и до 15 с ждёт их подтверждения, затем сигнал и только потом kill. Итог фиксируется в `branch_direct_stop_v1012`. Критерии подтверждённой остановки не ослаблены.
- 08_PRESERVE_DATA сохраняет все ротации журналов `.jsonl.N`. Хранение журнала диагностики увеличено до 9 файлов по 2 МиБ (~3 ч при наблюдавшейся скорости).
- Отчёты: незавершённая задача preentry после зависания помечается `ABANDONED_ON_STALL`. Локальная отсрочка RPC в лабораториях получает метку `RPC_DEFERRED` (backoff прежний). Добавлен раздел покрытия лаборатории выхода по сигналу. Квантиль p90 в отчёте расходов считается по nearest-rank (только диагностика).
- Панели: монитор с устаревшим heartbeat показывается как `NO_HEARTBEAT`, а не RUNNING. Для замороженного отчёта показывается время снимка. Округлены CPU, RAM и смещение часов. Украинский текст на /details переведён на русский.
- Тесты: кэш нативного чтения файлов монитора очищается между тестами (ложное падение при определённом порядке тестов).

Новая страница **/terminal** (http://127.0.0.1:8188/terminal) — компактная тёмная панель только для чтения: статус PAPER, капитал и PNL, позиции, входы и выходы, ветки, дорожная карта и диагностика. Работает без CDN, читает только существующие /overview и /api, ничего не меняет и в торговлю не вмешивается.

## Что не менялось

Стратегия, торговые пороги, размер позиции, лимит RPC (6/с, 4 in-flight, 0,75 с на допуск), правила свежести, условия продажи, финансовый журнал, бюджет проверки восстановления (600 с) и порог heartbeat (15/16 с). Ни один тест не пропущен и не ослаблен.

## Установка

1. Остановите старого бота штатно и дождитесь завершения процессов. Старую папку, её `results` и архивы preservation не удаляйте.
2. Распакуйте ZIP в **новую** папку. Не смешивайте файлы разных версий. 01_INSTALL, затем 02_SETTINGS (ключи только через настройки, private key не вводить, пороги не менять).
3. Для продолжения кампании перенесите **целиком** остановленную `app/data` старой папки в пустую `app/data` новой, как описано в RELEASE_NOTES_v101.md. Не переносите только primary.db. `control_failed.json` вручную не удаляйте. Старые `results/recovery_check_v89.json` и `acceptance_v90.json` не копируйте: они относятся к v0.7.101.1 и новой сборке не засчитываются (это намеренно).

## Порядок следующего Windows-теста

1. **04_CHECK** до конца, без Ctrl+C (около 4–5 минут, прогресс печатается каждые 20 с). Только после него пункт «Нативные проверки Windows» станет выполненным для v0.7.101.2. На сильно нагруженном ПК единично может упасть тест интервала `test_rpc94_keeps_six_per_second_spacing` (тайминг, не дефект лимитера): закройте лишние программы, повторите 04_CHECK и сохраните оба архива.
2. **14_RPC_STATUS**: нужны `after.status=READY`, `probe.status=PASS` и рост `started`.
3. **15_PAPER_FAULT_TEST** (два часа с инъекцией отказа через час) либо **03_START** (обычный PAPER, желательно не меньше 2 часов).
4. **STOP** штатно (Ctrl+C в окне бота или конец таймера 15_PAPER_FAULT_TEST).
5. **05_RESULTS**, затем **08_PRESERVE_DATA**. Пришлите обе папки/архива. При повторном зависании в них будет `*_stall_evidence_v1012.json`.

- Нативная проверка v0.7.101.2 на вашем ПК (нужен новый 04_CHECK) и полный двухчасовой PAPER-прогон.
- Выход через AMM на живом рынке (в запуске 0 из 11) и покрытие лаборатории выхода по сигналу при локальной очереди RPC.
- Прямая остановка веток при реальном зависании проверена только синтетически.
- Стратегия: 11 закрытий из минимум 100, вывода о прибыльности нет. Никакого разрешения live эта сборка не даёт.
